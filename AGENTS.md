# Emli — правила для разработчиков и ИИ-агентов

Этот файл читают все, кто пишет код в проекте: люди, Claude Code, Codex/GPT и другие агенты.
Здесь — как устроен проект, как в нём работать вдвоём и что нельзя ломать. Решили что-то важное — допиши сюда:
память агента у каждого своя и другому не видна, а этот файл общий.

## Что это

**Emli** — дневник питания, веса и тренировок с ИИ. Работает как **Telegram Mini App** (бот `@myemli_bot`)
и как обычный сайт. Пользователи в основном из **Беларуси**, язык интерфейса — **русский**.

Главное в продукте:
- дневник питания: поиск продуктов, штрихкоды, **еда по фото** и **чеки** через ИИ;
- нормы КБЖУ под цель, вес и талия, еженедельная проверка с подстройкой нормы;
- меню на неделю под норму + общий список покупок (realtime для участников меню);
- тренировки: программы, прогрессия, рекорды, карта мышц;
- соцчасть: друзья, лента, чаты, челленджи, достижения.

## Стек и устройство

| Часть | Что | Где |
|---|---|---|
| Клиент | Vite + React 19 + TypeScript, motion/react, TanStack Query | `src/` |
| Хостинг клиента | GitHub Pages, собирается сам при пуше в `main` (`.github/workflows/deploy.yml`) | `https://fronteggwp.github.io/emli/` |
| Бэкенд | Supabase (проект `ezhgiczvwsufzhwwwrkr`, Франкфурт): Postgres + RLS, RPC, Storage, Realtime | `supabase/` |
| Серверные функции | Supabase Edge Functions (Deno) | `supabase/functions/*` |
| ИИ | агрегатор a6 (`AI_BASE_URL`), OpenAI-совместимый `/v1/chat/completions` | функции `ai-food`, `ai-plan`, `barcode` |

### Клиент (`src/`)
- `pages/` — экраны, `sheets/` — нижние шторки, `ui/` — общие компоненты, `nav/` — навигация.
- Навигация своя: `useNav()` → `nav.push(<Screen/>)`, `nav.sheet(<Sheet/>, { full })`, `nav.setTab(...)`; закрыть текущий слой — `useLayer().close()`.
- Данные: `src/data/*` — хуки TanStack Query поверх Supabase (`api.ts` — дневник, вес, продукты; `engage.ts` — шаблоны, рецепты, ИИ по фото; `mealplan.ts` — меню и покупки; `workouts.ts`, `social.ts`, `insights.ts`). Мутации — с оптимистичным обновлением, ошибки ловит общий обработчик (тост «Не сохранилось»).
- Чистая логика без React — `src/lib/*` (`nutrition.ts` — нормы и расчёты, `mealplan.ts` — составление меню, `exercise.ts`, `progression.ts`, `dates.ts`, `telegram.ts` — обёртка Telegram WebApp).
- Стили: обычный CSS рядом с компонентами + токены в `src/styles/global.css` (`--card`, `--text`, `--kcal`, `--protein`, `--fat`, `--carbs`, `--good`…), тёмная и светлая тема. Новые цвета — через токены, не хардкодом.
- «Что нового» после обновления — `src/data/releases.ts` (см. ниже).

### Серверные функции (`supabase/functions/`)
| Функция | Зачем |
|---|---|
| `tg-auth` | вход: подпись Telegram (или тестовый ключ) → токен Supabase |
| `ai-food` | еда по фото и чеки: модель смотрит фото → продукты → поиск в базе и выбор моделью (до 3 кругов) → КБЖУ по базе |
| `ai-plan` | меню на неделю: модель только выбирает блюда и раскладывает по дням, порции/КБЖУ/покупки считает `src/lib/mealplan.ts` |
| `barcode` | поиск по штрихкоду: Open Food Facts → наша база → этикетка через ИИ → оценка |
| `food-search` | поиск товаров: наша база штрихкодов + Open Food Facts; белорусские товары — первыми |
| `tg-bot`, `notify`, `reminders` | бот, уведомления, напоминания |
| `account` | экспорт и удаление аккаунта |

ИИ-модели: фото и чеки — `kimi-k3`, запасная через 15 с — `claude-sonnet-5` (`AI_VISION_MODEL` / `AI_VISION_BACKUP`); выбор продуктов в базе — `deepseek-v4-flash` (`AI_PICK_MODEL`); прочий текст — `deepseek-v4.1-flash` (`AI_MODEL`).
Поставщики на агрегаторе меняются молча: модель может перестать видеть картинки или замедлиться в разы. Если распознавание «выдумывает» блюда — первым делом прогнать фото напрямую и посмотреть число входных токенов (без картинки их мало).
Особенности a6, на которых уже обожглись:
- рассуждения выключаются по-разному: gemini — только `reasoning_effort: "none"`; остальным — `thinking: {type:"disabled"}` + `enable_thinking: false` (а `reasoning_effort` им, наоборот, **включает** рассуждения) — см. `noThinking()` в `ai-food`;
- часть поставщиков (gemini, claude) **не скачивает фото по ссылке** — поэтому фото всем моделям идёт внутри запроса (base64);
- тело запроса сжимаем gzip, ответ может прийти потоком даже при `stream: false` — разбирать через `replyText()`.

### База
- Миграции — `supabase/migrations/ГГГГММДДЧЧММСС_что_делает.sql`. RLS включён везде: свои данные видит только владелец, чужие — через security-definer RPC.
- `service_role` ключ — **только** в серверных функциях, никогда в клиенте.

## Как работаем вдвоём

Команда: **Дмитрий** (GitHub `@fronteggwp`, владелец проекта) и **@silvestrr**, у каждого свой Claude.
Главное правило: **`main` — это то, что сейчас у пользователей.**

Что включено на GitHub (защита ветки `main`):
- прямой пуш в `main` закрыт для всех, включая владельца; удалять и перезаписывать `main` нельзя;
- мерж — только через PR и только при зелёной проверке **`check`** (`.github/workflows/ci.yml`: `npm test` + `npm run build`);
- PR, которые трогают базу, вход или CI (`.github/CODEOWNERS`), требуют одобрения **второго** человека;
- все обсуждения в PR должны быть закрыты; мерж — squash, ветка удаляется сама; можно включать автомерж (`gh pr merge --auto --squash`).

1. **Задача → ветка → PR.** Ветка от свежего `main`: `имя/коротко-о-задаче` (например `dima/receipt-scanner`). Взял задачу — отметь в GitHub Issues, чтобы второй не делал то же самое.
2. **В `main` — только через Pull Request.** Прямой пуш в `main` и `--force` в общие ветки — нельзя.
3. **PR маленькие** — на 1–2 дня. Перед мержем подтяни ветку к свежему `main`.
4. **Перед PR обязательно:** `npm run build` (типы + сборка) и `npm test` — оба зелёные.
5. **Зоны:** договариваемся, кто какой частью занимается, чтобы два агента не правили одни и те же файлы. Общие «горячие» файлы — `App.tsx`, `global.css`, `data/api.ts`, `lib/types.ts`, `data/releases.ts`: правки в них — маленькие и точечные.
6. **Не мержатся без второго человека** (даже если ИИ-ревью сказало «ок»): `supabase/migrations/` (в т. ч. правила доступа RLS), `supabase/functions/tg-auth/`, `.github/` — это закреплено в `.github/CODEOWNERS`.
7. **Описание PR** — по шаблону: что сделано, как проверено, есть ли миграция и какие функции нужно задеплоить.

### Деплой
- Клиент выкладывается сам из `main` (GitHub Pages).
- Серверные функции и миграции: цель — тоже только из `main` через GitHub Actions. **Пока это не настроено, деплой функций и `db push` делает только владелец проекта (Дмитрий)** и только из актуального `main` — иначе можно молча затереть чужую версию функции.
- Миграции: только новые файлы; уже применённую миграцию **никогда не редактировать** — исправление отдельной миграцией. Опасное (удаление колонок/таблиц) — отдельным PR.

### Коммиты
- Сообщения коммитов — на **русском**: заголовок о сути изменения, ниже списком — что и зачем.
- Коммит от ИИ-агента заканчивается строкой соавторства этого агента (например `Co-Authored-By: Claude …`).

## Правила продукта (не нарушать без обсуждения)

- **Белорусские товары — первыми.** В поиске и при выборе товара ИИ белорусские (штрихкод `481…` или страна продажи «Беларусь») идут первыми; российские — запасной вариант.
- **Внешние данные — по API по запросу**, плюс наша растущая база (штрихкоды, этикетки от пользователей). Целиком чужие базы не выкачиваем.
- **ИИ по фото раскладывает блюдо на продукты**, КБЖУ — по продуктам из базы; готовые блюда и рецепты в кандидаты не берём. Под продуктом видно, что взято из базы.
- **Вес:** везде показываем **последнее взвешивание**; изменения — по истории взвешиваний; сглаженный тренд — только для расчётов и линии на графике.
- **Калории тренировки** считаются по подходам и отдыху; таймер ограничивает их, только если за это время подходы физически можно было сделать.
- **«Что нового»** (`src/data/releases.ts`): новая заметная функция для пользователей → новая запись **в начало** списка с новым `id`. Только новые возможности, **исправления ошибок не пишем**. Тексты короткие.
- **Тексты интерфейса** — по-русски, на «ты», коротко и по-человечески. Без канцелярита.

## Грабли, на которые уже наступали

- **В базу — только колонки таблицы.** Объекты из поиска/списков содержат лишние поля (`uses`, `last_used`, `origin`, `by`…), и вставка падает целиком. Для `food_entries` и `foods` — whitelist в `src/data/api.ts` (`pick(…, ENTRY_COLS / FOOD_COLS)`); для новых таблиц делать так же.
- **StrictMode монтирует компоненты дважды** в разработке: одноразовые эффекты (показ окна, обмен токена) не завязывать на `useRef`-флаг при монтировании.
- **Telegram WebView:** геолокация и таймеры работают только пока приложение на экране; шагов/здоровья из Mini App не достать.
- **Не хранить данные пользователей в `localStorage`** как источник правды — только удобства. Общее между устройствами — Supabase или `CloudStorage` Telegram (`cloudGet/cloudSet` в `lib/telegram.ts`).

## Секреты и доступы

- Репозиторий публичный (скоро станет приватным). **Никаких ключей в коде, коммитах, PR и чатах.**
- Локальные ключи — в `.env.local` (в git не попадает): `VITE_DEV_LOGIN_SECRET`, `AI_BASE_URL`, `AI_API_KEY`, `ADMIN_SECRET`, `PEXELS`. Публичные `VITE_SUPABASE_URL` и `VITE_SUPABASE_KEY` — в `.env` (а в коде есть запасные значения).
- Секреты функций — в Supabase (`supabase secrets`): `AI_*`, `TELEGRAM_BOT_TOKEN`, `WEBHOOK_SECRET`, `NOTIFY_SECRET`, `ADMIN_SECRET`, `DEV_LOGIN_SECRET`, `APP_URL` и др.
- Передавать ключи друг другу — через менеджер паролей, не в мессенджере. У каждого разработчика — свой ключ ИИ.
- Публичные ссылки на медиа в Storage — известная тема; не менять без решения владельца.

## Как запускать и проверять

```bash
npm install
npm run dev          # http://localhost:5173
npm run build        # проверка типов + сборка
npm test             # тесты алгоритмов (tools/algo-test.ts)
```

- Вход в разработке без Telegram: `http://localhost:5173/?dev=1` (или `?dev=2`, `?dev=3`) — тестовые аккаунты «Тестер N», нужен `VITE_DEV_LOGIN_SECRET` в `.env.local`. Тестовые аккаунты скрыты от обычных пользователей.
- Сквозные проверки ИИ: `node tools/ai-food-test.mjs`, `tools/barcode-test.mjs`, `tools/ai-plan-test.mjs` (ходят в настоящие функции под тестовым аккаунтом). Лимит ИИ по фото — 40 запросов в сутки на аккаунт.
- Тестовые данные, созданные при проверке, — удалять за собой. Реальные аккаунты пользователей не трогать.

## Ревью кода (для людей и ИИ-ревьюеров)

Блокировать мерж — только за серьёзное:
- баг, который ломает сценарий пользователя или теряет/портит данные;
- уязвимость: обход RLS, `service_role` в клиенте, утечка ключа, доверие данным клиента на сервере;
- нарушение правил из этого файла (миграции, белорусские товары, вес, «Что нового»…);
- сломанные `npm run build` / `npm test`.

Стиль, имена, мелкие улучшения — комментарием, без блокировки.
